# T3c: the web page on the T5 — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The web page shows and edits a T5 the way it does the RLCD: the panel's size, aspect and grays in every screen image, the radar's zoom in the T5's kilometres, nothing for hardware the T5 lacks; and the T5's gray BMPs checked over Wi-Fi.

**Architecture:** `/api/layouts` (`ui_catalog.c`) already publishes the board, the panel's size, its status bar, the capabilities and the split's rules (T0). It gains the panel's bits per pixel and the Radar layout's map (its size and the board's zoom step). `web/app.js` loads that catalogue once, before any page that needs it, and takes from it every number it fixes today: the screen images' aspect and width, the radar's kilometres, and which hardware rows to show. The firmware embeds `web/`, so both boards get the page with their next image; the RLCD's page looks and behaves as before.

**Tech Stack:** C17 (`components/ui`, host-tested with Unity), plain JavaScript (`web/app.js`, tested with Node's test runner against a fake device), ESP-IDF 5.5.5, the T5 over Wi-Fi with curl and a Chrome driven over CDP (argent).

**Spec:** `docs/specs/2026-10-06-t5-board-design.md` (r7): §7.4 (the web UI), §6.5 (the gray BMPs), §4.3 (capabilities), §9 (Web), §11 (T3c), §12 (RainViewer's loop at 960 px).

## Global Constraints

- The RLCD's goldens stay byte-identical; both boards build clean with no new warnings (`tools/idf.sh build`, `REFLBO_BOARD=t5 tools/idf.sh build`).
- Host suite: `cmake --build build-host` then `ctest --test-dir build-host` (72 tests; ctest runs `test/web/test_app.mjs` when node is found). Run the two commands separately, not inside `sh -c`.
- The RLCD's page is unchanged in what it shows and sends: every existing web test passes unedited apart from its fixtures gaining the catalogue's new fields.
- The fork's design lives in the T5 spec, not in edits across the upstream spec (T5 spec §3); AGENTS.md's T5 notes go in its §10.
- Board rules (AGENTS.md §10, quick rule 3): flash only `/dev/cu.usbserial-52D60046741` after reading MAC `34:ab:95:5e:5d:58`, with `-b 230400`; never erase; back up the board's configuration (`GET /api/backup`) before a test that changes it and restore it after (`POST /api/restore`), then compare.
- The owner's web password is theirs: never reset it, never ask for it in text. The owner types it into a browser window this Mac opens; the checks use that session and log it out at the end.
- Commits: Conventional Commits, imperative, no trailers, no mention of tools or assistants.

## Review Focus

1. **The catalogue fails to load once** (a dropped request on a phone's Wi-Fi): the page shows its error with Try again, and Try again loads it, instead of keeping the failure for the session. Pinned in Task 2.
2. **A save from the Device page on the T5** must not change what the page no longer shows: the PATCH leaves out the sensor offsets and the refresh rate, so the file keeps them as they were (T5 spec §9). Pinned in Task 4.
3. **The RLCD's page** must not change: its images keep the 400 px, 4:3 and pixelated look, its radar the same kilometres, every row shown. Pinned in Tasks 2, 3 and 4 (each new test also runs the RLCD's catalogue).
4. **A preset made on the RLCD** and restored on the T5 (a backup across boards): its slot tags land in the T5's preview by percentages of the T5's panel, not the RLCD's. Pinned in Task 2.
5. **A browser that can't show a 4-bit BMP** would leave every preview blank on the T5. Chrome is checked at the board (Task 5); the owner's phone browser is an owner check listed in Task 6.
